# Project audit — 2026-09-17

Five agent-driven dimensions: auth/authz, data integrity + money, Next.js 16 correctness,
test coverage, performance. Read-only. Nothing was changed by this audit.
Every finding below was re-verified by hand against the cited line.

## P0 — fix first

### 1. Error boundaries call a prop that does not exist
`src/app/error.tsx:13,16,39`, `src/app/global-error.tsx:9,12,37`

Both destructure `unstable_retry`. Next.js 16.3.5 passes `retry`.
Verified: `node_modules/next/dist/client/components/error-boundary.js:114` -> `retry: this.retry`.
Verified: `docs/.../error.md:331-332` — "v16.3.0 `retry` prop became stable / v16.2.0 `unstable_retry` prop added".
`unstable_retry` appears nowhere in the Next runtime — only in that changelog row.

`unstable_retry` is `undefined`. Clicking "Try again" throws `TypeError` inside the error
boundary itself. This is the app's only recovery UI, and it is broken app-wide including
the root layout fallback.

Fix: rename the prop to `retry` in both files (6 lines).

### 2. Five endpoints bypass the session revocation ledger
`src/app/api/backups/[id]/download/route.ts:8`, `src/app/api/reports/export/route.ts:11`,
`src/app/api/reports/expiry/export/route.ts:19`, `src/app/api/uploads/route.ts:14`,
`src/actions/notifications.ts:8,21,34`

These call `auth()` directly and test only `session?.user`. `src/lib/store-context.ts:24-56`
is the code that actually checks `UserSession.revokedAt`, `expiresAt`, and `user.status` — its
own doc comment says the edge check is not enough and "this is the check that actually rejects it".
`src/proxy.ts:77` excludes `api`, so nothing else covers these routes.

Exploit: a stolen 30-day rememberMe cookie survives "log out everywhere", an admin
deactivation, and an admin-forced password reset. The attacker can still download a full
database backup via `/api/backups/[id]/download`.

Fix: swap `auth()` for `getStorelessSessionContext()` at all five sites.

### 3. Admin actions never revoke sessions
`src/actions/stores.ts:122` toggleStoreStatus, `src/actions/managers.ts:192` transferManager,
`src/actions/users.ts:112` toggleSellerStatus, `src/actions/users.ts:172` resetSellerPassword,
`src/actions/managers.ts:170` resetManagerPassword

Self-service `changePassword` (`src/actions/account.ts:43`) correctly revokes every other
session. No admin action does. Worst case is the password reset: a manager resets a seller
password *because* it is compromised, and the attacker's live session keeps working.

Fix: `userSession.updateMany({ where: { userId, revokedAt: null }, data: { revokedAt: new Date() } })`
in each of the five actions.

## P1 — data correctness

### 4. Concurrent partial returns lose money
`src/actions/sales.ts:509` reads the sale via `prisma.findFirst` *outside* the transaction;
`:688-698` writes `subtotal`/`discount`/`tax`/`total`/`netProfit`/`refundedTotal` as absolute
values computed from that stale snapshot, with no `WHERE total: sale.total` guard.

Sale total 100, item A 30, item B 70. Two managers return A and B at the same moment; both
read total=100. Tx1 -> total 70 / refunded 30. Tx2 -> total 30 / refunded 70. A's 30 vanishes.
Should be total 0 / refunded 100. Stock is fine (guarded increments); the ledger is not.

Fix: move the `findFirst` inside the `$transaction`, or use relative `decrement`/`increment`
on the money columns.

### 5. Product edit resurrects sold stock
`src/actions/products.ts:255-276` — `existing` is read outside the transaction and
`tx.product.update` writes `stock` as an absolute value with no optimistic guard.
`src/actions/batches.ts:429` does this correctly (`updateMany({ where: { stock: oldStock } })`
-> throws `Conflict` on `count === 0`); the product path does not.
Same shape at `src/actions/variants.ts:183-192`.

Stock 50. A manager opens the edit form. A cashier sells 3 -> 47. The manager saves (form still
carries 50) -> stock back to 50 with 47 on the shelf. The movement it logs is `50 - 50 = 0`,
so the audit trail does not even record the discrepancy. Next sale oversells.

Note `updateProduct` already blocks this correctly for batch-tracked products
(`src/actions/products.ts:238`) — the guard just does not extend to the ordinary path.

Fix: `updateMany({ where: { id, stock: existingStock } })` and reject on `count === 0`,
matching the batch path.

### 6. Low-stock alerts never fire for variant products
`src/actions/sales.ts:449-452` filters on `Product.stock`. For `hasVariants` products that
column is stale by design — `createSale` only ever calls `decrementVariantStock`.
A size that sells to 0 leaves the parent frozen at its initial value, `100 <= 5` is false
forever, and no manager is ever told.

Fix: for `hasVariants` products, compare the variant rows instead.

### 7. `createProduct` is not transactional
`src/actions/products.ts:152` create, `:178` initial InventoryMovement, `:190`
persistAttributeValues — three separate statements. `createVariant`
(`src/actions/variants.ts:91-125`) wraps the identical pattern in `$transaction`.
A crash between them leaves a product with stock and no movement explaining it.

## P1 — performance

### 8. Invoice numbering does a full table count inside the sale transaction
`src/actions/sales.ts:324` and `src/lib/api/orders.ts:217` — `tx.sale.count({ where: { storeId } })`
while stock rows are locked. Invisible at 500 sales; ~50-150 ms of extra lock window at 50k;
at 500k cashiers serialize and burn `MAX_INVOICE_ATTEMPTS = 5`.
Fix: a per-store counter row or a Postgres sequence.

### 9. Unbounded queries that grow with the table
- `src/lib/queries/users.ts:10` — `getSellers` pulls every sale row per seller to sum in JS (`:25`). Use `groupBy`.
- `src/lib/queries/reports.ts:41` — whole period of sales fetched, bucketed in JS (`:46-72`). ~10 MB at 50k/yr. Use `date_trunc GROUP BY`.
- `src/lib/queries/sales.ts:10-24` — `getPOSProducts` has no `take` (the `LIST_CAP` declared at `:6` is unused here) and eagerly joins every variant. 100k+ rows per POS open at 20k SKUs.
- `src/lib/queries/dashboard.ts:57` — 30 days of saleItems with a nested category join, grouped in JS (`:110-117`).
- `src/lib/queries/dashboard.ts:53` — 14 days of sales fetched to produce 14 numbers.
- `src/lib/queries/dashboard.ts:42,:198` and `src/lib/queries/stores.ts:175` — whole product table pulled for three scalars.
- `src/lib/queries/messages.ts:66,:28` — no `take`, no cursor; list sorted in JS at `:56`.

### 10. Two missing indexes
- `src/lib/queries/products.ts:8-11` — `storeId` + `orderBy createdAt desc`. Existing indexes are `(storeId,status)`, `(storeId,name)`, `(storeId,trackBatch)`, `(storeId,updatedAt)`. Add `@@index([storeId, createdAt])`.
- `src/lib/queries/sales.ts:87-90` — SELLER path filters `sellerId` and sorts `createdAt desc` against `@@index([sellerId])` alone. Add `@@index([sellerId, createdAt])`.

### 11. Sequential awaits that should be `Promise.all`
`src/app/(dashboard)/dashboard/page.tsx:45 -> :140 -> :220`, plus `stores/[id]/page.tsx:25->:28`,
`account/page.tsx:19->:24`, `variant-axes/page.tsx:16->:19`. Fixed ~100-200 ms per render on Neon.

## P2

### 12. No segment-level `error.tsx` under `(dashboard)`
All 19 segments have `loading.tsx`; none has `error.tsx`. Per `docs/.../error.md`, an error
boundary does not cover the layout at its own level, so any dashboard page failure blows past
`(dashboard)/layout.tsx` and blanks the whole shell including navigation.
Fix: one `src/app/(dashboard)/error.tsx`.

### 13. `changePassword` does not revalidate
`src/actions/account.ts:10-66` revokes every other session but never calls `revalidatePath("/account")`.
Its siblings `terminateSession` (`:90`) and `terminateAllOtherSessions` (`:111`) do.
The Sessions tab keeps showing the just-killed sessions as active.

### 14. `round2` mis-rounds exact .xx5 boundaries
`src/lib/sale-math.ts:7` — `Math.round(n * 100) / 100`. Verified in node:
`1.005 -> 1` (not 1.01), `1.015 -> 1.01`, because `1.005 * 100 === 100.49999999999999`.
Systematic one-cent underbilling on those inputs. Low frequency, real.

## Test coverage gaps

`npm test` is 217/217 green, but the pattern is consistent: **pure calculation is tested
well; the Prisma-transaction orchestration and the auth/RBAC boundaries around it are not
tested at all.** 15 test files, none of which import `src/lib/inventory.ts`,
`src/actions/sales.ts`, `src/actions/batches.ts`, `src/lib/rbac.ts`, or `src/lib/auth.ts`.

Worst gaps, in order:
1. `src/lib/inventory.ts` — the oversell defense, no test file exists. Moving the `stock: { gte: quantity }` guard out of `updateMany`'s WHERE into a separate read-then-write would reintroduce the race and nothing would fail.
2. `src/actions/sales.ts` — createSale/deleteSale/returnSaleItems. A param swap between `planReturnRestoration` (tested) and `incrementBatchStock` (untested) silently over- or under-restores stock.
3. `src/actions/batches.ts` — distinct from the well-tested `src/lib/batches.ts`. Nothing proves the action actually calls `assertReconciled`.
4. `src/lib/rbac.ts` — the permission matrix is plain data. Adding `"sale.refund"` to SELLER compiles and every test still passes.
5. `src/lib/rbac-guards.ts::requireStorePermission` — tenant isolation, the highest-value invariant in the app, asserted nowhere. `src/actions/user-data.test.ts` mocks it away entirely.
6. Session revocation — no test revokes a session and confirms the next request is rejected.
7. `src/lib/auth.ts` — `tryConsumeRecoveryCode` untested; a replayable recovery code would ship silently.
8. E2E is smoke-level. `e2e/dashboard-smoke.spec.ts` only asserts 19 GET routes return <400. Nothing ever POSTs a sale. A broken `/sales/new` submit handler passes CI as long as the page renders.

Well covered, genuinely: `sale-math.test.ts`, `batches.test.ts` (the strongest file in the
repo), `encryption.test.ts` / `totp-encryption.test.ts`, `storage/backups.test.ts`, `api/keys.test.ts`.

## Clean — checked and found nothing

- RBAC matrix itself (`src/lib/rbac.ts:31-74`): no escalation path. SELLER holds nothing MANAGER-only; `requireStorePermission` always sources `storeId` from the session, never from input.
- Cross-tenant IDOR: every non-trivial `findFirst`/`findUnique`/`updateMany` across products, sales, batches, categories, colors, sizes, variants, variant-axes and catalog-templates scopes by session `storeId`.
- Next.js 16 async `params`/`searchParams`: clean everywhere. No sync `cookies()`/`headers()`/`draftMode()`. No `"use client"` file imports prisma or auth directly.
- Concurrency core: `src/lib/inventory.ts` and `src/actions/batches.ts:429` both guard correctly inside the WHERE. `createSale`/`deleteSale` are fully transactional with the right stock grain.
- Schema FK cascades: `SaleItemBatchAllocation -> ProductBatch` is Restrict and `SaleItem -> Product` defaults to NO ACTION, so history blocks deletion. No missing constraints found.
- N+1 loops: bounded by cart size, not table growth.
